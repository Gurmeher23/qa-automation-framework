# Test strategy

This is the strategy the framework implements, written as I would hand it to a team that has no automated QA yet.

## 1. Goals

1. Catch regressions in the critical business paths (login, create order, order state changes, admin overview) before a merge.
2. Give developers feedback fast: smoke in about a minute, full suite in minutes, not hours.
3. Make every failure diagnosable from the CI artifacts alone (report, screenshot, trace, triage summary).
4. Keep the suite cheap to maintain: few, stable UI tests; many fast API tests.

## 2. Test pyramid

| Layer | Folder | Count (see README for the current run) | Runs against | Purpose |
|---|---|---|---|---|
| Unit | `tests/unit` | tooling only | no server | Logic of the framework's own triage tool |
| API | `tests/api` | the largest layer | live HTTP server | Business rules, validation, auth, pagination, idempotency |
| UI | `tests/ui` | the smallest layer | live server + Chromium | A few end-to-end user journeys and the one piece of client-side logic (admin filter) |

Rules of thumb used when deciding where a test belongs:

* Anything that is a rule of the system (status transitions, validation limits, ownership) is an API test. It is 20 to 50 times faster than the same check through a browser and has no rendering flakiness.
* A UI test exists only if the browser is part of the behaviour: form submission, redirects, rendered messages, client-side JavaScript.
* UI tests arrange state through the API (fresh user, cookie injected into the browser context) and only drive the screen under test. The login form has its own tests; no other test pays for it.

## 3. Smoke vs regression

* `smoke` (13 tests): the shortest set that proves the application is usable: health, login, auth guard, create and fetch an order, one status path, idempotent retry, first page of the list, create an order in the browser, admin visibility. Budget: under one minute. Runs on every push and on every merge request.
* `regression`: the full suite, which includes the smoke tests. Runs on pull requests to the main branch and nightly (schedule the same pipeline).
* A test is promoted to smoke only if its failure would mean "stop, the build is unusable". Edge cases and validation matrices never go to smoke.

## 4. Test data strategy

* **Isolation by construction.** Each test gets a freshly provisioned user (via the admin API) and creates its own orders. Users only see their own orders, so tests cannot interfere, which makes parallel runs safe without locking.
* **Deterministic factories.** `tests/data/factories.py` draws values from a seeded RNG (`TEST_SEED`, default 1234). Identifiers that must be unique (usernames, customer tokens) use a random suffix, so reruns on a shared stage do not collide.
* **Seeding through the API.** `tests/data/seed.py` uses the public API, not the database. The same code therefore works against the local server, the Docker stage and any other environment, and it exercises the admin endpoints as a side effect.
* **Baseline dataset.** `seeded` creates orders in the new, paid and shipped states under a unique token. The admin filter tests assert exact counts on that token, which stays correct even while other tests add rows concurrently.
* **No production data.** Nothing here reads or copies real customer data. For a real engagement the equivalent is synthetic data generated by factories plus anonymised snapshots only if legally cleared.
* **Cleanup.** Local runs use a throwaway SQLite file per xdist worker. The Docker stage is reset with `make stage-down` (removes the volume).

## 5. Environments

| Environment | How | Used for |
|---|---|---|
| Local | `make test` (app in a thread, SQLite) | Developer feedback, CI |
| Stage | `make stage-up` (Docker image + PostgreSQL), then `make stage-test` | Production-like checks: real database engine, real container, same image as deployment |

`BASE_URL` switches the suite from "start my own server" to "test that deployment". Credentials come from environment variables, never from the repository.

## 6. Flakiness policy

1. A flaky test is a bug in the suite. It is fixed or quarantined within a week; it is never left red "because it is usually fine".
2. No `sleep`. UI tests use Playwright auto-waiting and `expect(...)` web-first assertions; the HTTP tests need no waits at all.
3. No blanket retries. A retry hides the signal. If a retry is ever added (for example `--reruns 1` on stage only), the rerun must be visible in the report and counted in a flakiness metric.
4. Quarantine means: mark with a dedicated marker, exclude from the blocking pipeline, keep running it in a non-blocking job, and open a ticket with an owner.
5. Triage first: `python -m triage reports/junit.xml` groups failures by similar stack trace. One group of 20 failures is one problem, not twenty.
6. Evidence is automatic: UI failures keep a screenshot and a Playwright trace (`npx playwright show-trace trace.zip`).

## 7. CI integration

* Stages: lint (ruff), API and unit tests, UI tests. Lint failure blocks everything else.
* Artifacts: HTML report, JUnit XML, screenshots and traces are always uploaded.
* On UI failure, the triage summary is appended to the job summary (GitHub) or printed in the job log (GitLab).
* The same pipeline definition exists for GitHub Actions and GitLab CI. An Azure DevOps version would map one to one (script steps plus `PublishTestResults` for the JUnit file).

## 8. What is deliberately not covered

Performance and load testing, accessibility audits, visual regression, cross-browser matrices, security testing and contract testing are not part of this repository. They are the natural next layers once the pyramid above is stable; adding them before that would be premature.

## 9. Quality gates proposed for a real team

* Merge request: lint + smoke must pass.
* Main branch: full regression must pass.
* Release candidate on stage: full regression against the stage deployment plus a manual exploratory session on the changed areas.
* Track, per week: pass rate, flaky-test count, time to first feedback, and mean time to diagnose a failure.
